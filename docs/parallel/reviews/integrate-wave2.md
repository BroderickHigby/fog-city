**New findings**

1. **High: route planning is quadratic per re-route on the SF graph.** `src/sim/vehicles/follower.ts:44` (`nearestLane`) scans all 15,671 edges in both directions on every call. `:64` re-sorts the whole queue on every Dijkstra pop, with a cap of 4×9,441 visits.
   - Scenario: a heat-2 van pursuing a driving player re-routes whenever the target moves more than 12 m (`:124`), about every second, per van. Spawn checks (`service-runtime.ts:138`, `transit-runtime.ts:72`) also run full routes for each candidate point. On the SF world each re-route is likely tens to hundreds of ms of frame hitch; I estimated this from complexity and did not measure it.
   - Fix: a binary heap, a spatial index for nearest lane, and caching nearest lanes per goal.

2. **Medium: `step()` throws on ordinary gameplay conditions, with no recovery.** `motion.ts:96` throws on a blocked spawn, `follower.ts:118` on a teleport over 50 m, and `identity.ts:16` when identity capacity is exceeded. `main.ts:247` has no catch.
   - Scenario: an admission check that disagrees with the planner, or an id leak, permanently freezes the game.
   - Fix: reject the proposal and keep it staged, emit an event, and never throw from a gameplay condition.

3. **Medium: identities grow without bound.** `src/sim/identity.ts:10-23` never prunes bindings, and `:16` sorts every binding on each new id.
   - Scenario: each 10-minute transit departure (`transit:${route}:${minute}`) and each heat van adds a permanent id. State size and cost grow all session, and the game throws at 32,768 ids.
   - Fix: release ids of retired actors and keep a running count.

4. **Medium: runtime walkers ignore other bodies.** In `motion.ts:159-169`, a walker motion checks only world geometry and vehicle hulls, not player walkers or other agents. Vehicles also check stale poses (`:177`) while walkers move at the same time.
   - Scenario: a mission robot walks into the player on foot and the two overlap until the next tick's capped push.
   - Fix: test against `obstacles().circles` and against motions already accepted this tick.

5. **Medium: changes to the composed path are not pinned.** All vitest replays use `systems=[]`. Commits after the v7 bump (`93e32c3`, `ac230bd`, `6a9cd35`) changed behaviour with combat and agents composed, with no version bump and no failing pin.
   - Fix: add a pinned golden replay that runs through `createGameSystems()`.

6. **Low: combat walls ignore `underY`.** `combat/adapter.ts:53` sets `minY:baseY`, but bodies may pass under structures (`world.ts:241`).
   - Scenario: a player under a skyway starts "inside" a wall, so every shot is blocked at once (`physics.ts:47-66` returns 0).
   - Fix: set `minY = underY ?? baseY`. Latent: no data produces `underY` yet.

7. **Low: wall contact at the start point now blocks attacks.** `combat/attacks.ts:87` dropped the old `hi>1e-6` guard, so a start point touching a facade now counts as blocking.
   - Scenario: a robot flush against a wall, attacking away from it, is blocked.
   - Fix: ignore contacts at a fraction of about 0.

8. **Low: `prepare` player changes are silently discarded.** `step.ts:399-404` rebuilds `players` from the pre-`prepare` copy, so any player change a `prepare` hook makes is lost.
   - Fix: reject such changes in `prepareSystems` (`systems.ts:59`).

9. **Low: `dayIndex` rolls over at 08:00.** `clock/calendar.ts:57` sets `dayIndex` to elapsed ÷ `DAY_TICKS` and ignores the epoch hour, so it changes at 08:00 while the calendar date changes at midnight. `game-systems.ts:45` passes both to gameplay.
   - Fix: base `dayIndex` on `absoluteDay - epochDay`.

10. **Low: per-substep obstacle rebuild.** `motion.ts:36-56` rebuilds every circle and box for every player and agent on each vehicle substep (`:177`), plus an O(R²) robotaxi pair loop (`:116-128`). That is fine now but will not scale.
    - Fix: build obstacles once per tick and use a spatial hash.

## agents-player

**Fog City review: agents and player, ee21b4d..c36a550 (origin/integrate/wave2)**

**Verdict: request changes.** The top safety concern is fixed in substance. Every person and animal body made at runtime now joins `ext.agents.list` and goes through the dodge override. But the proof is thin: the no-touch fuzz never runs runtime bodies or controlled vehicles. Separately, claimed ambient bodies are never culled. That freezes pedestrians in place and eventually crashes the sim. Several player-side gaps from the earlier review are still present.

How I checked: read-only git and code reading at c36a550. I ran no tests. Every forbidden-API grep of `src/sim` came back clean.

**Earlier findings**

Agents:
- **`systems=[]`:** FIXED for the shipped game. `src/sim/agents/systems.ts:106` is still `[]`, but `createGameSystems` builds the agents system (`game-systems.ts:21`) and `main.ts:205` uses it. The default `SYSTEMS` list still has no agents or combat.
- **Runtime bodies outside the clearance set:** FIXED in substance.
  - `motion.ts:85-101` admits runtime bodies into `ext.agents.list`. Animals and unknown kinds become protected persons.
  - `dodge.ts:224-228` puts every runtime person in class `person` or `care` (child, protected, mobility aid, seated or lying), so all are under the override. Robots are left out by design.
  - Runtime vehicles: walkers are blocked from closing on a vehicle box (`motion.ts:160-169`). Vehicle sweeps are blocked by person circles (`occupied`). `stepDodge` then runs on all of them.
  - `dodgeOverrideActive:false` is still hard-coded (`agents/runtime.ts:325`). It is only cosmetic now, because `applyMotionBodies` ignores a body's proposal while it is mid-dodge.
  - In production nothing spawns children, dogs or seated people yet.
- **`badRobotRate` uses `Math.hypot`:** STILL PRESENT. `src/content/places.ts:105` (`distanceM`) is reached through `agents/runtime.ts:132` and `game-systems.ts:22`. It decides each robot's good or bad firmware.
- **`ThreatVanRequest` mismatch:** FIXED in the live path. `service-runtime.ts:46-58` uses `ThreatSpawnRequest`. The old `ThreatVanRequest` with `id:number` survives only in test-only `services.ts:76`.
- **O(n² log n) `propose()`:** mostly fixed. Nothing sorts inside the loop any more. `observationSet` (`runtime.ts:234`) is still O(bad robots × n).

Player:

- **Runway attribution:** FIXED. `adapter.ts:33` flips player and actor for `player.*` events.

  - `idleWindowS` in the content is ignored.

  - `missions/system.ts:21` sorts `campaign??0` first, so `ramen-pitch` (no campaign) is picked at line 32.
  - Its first step is a phone-call trigger, so hot-desk never auto-starts. Only the explicit `mission-start` sent by `main.ts:236` hides this.

**Also checked**
- **Mission staging until physical admission:** partly done. Retries are bounded (`agents/systems.ts:57`, two per tick, every 30 ticks). But the `stage` step returns `next` straight away (`missions/system.ts:51`), so objective clocks start before the actors exist. This is safe for the current content only because each staged actor is first needed by an objective with no time limit. A placement that never succeeds soft-locks the mission silently.

Live state is hashed against a replay in the same Chromium page, with no pinned hashes or roadmap numbers (`tests/e2e/campaign.spec.ts:128-138`). `policy-replay.test.ts` compares two runs of the same code and does not touch `runtime.ts` or `motion.ts`. `determinism.spec` is a real Node-versus-browser check.
- **No-touch fuzz:** it runs only the default `SYSTEMS` (`tests/sim/dodge-scenes.ts:400`), so legacy bodies only. `runtime-walker-clearance.test.ts` covers parked vehicles only.

**New findings**

1. **High: claimed ambient bodies never despawn, which freezes them and later crashes the sim.** `src/sim/agents.ts:1980-1984`, `agents/runtime.ts:192`, `motion.ts:85`.
   - Every legacy person or robot within 300 m gets a proposal each tick, so it is claimed and marked `runtimeId`.
   - `stepAgents` then skips claimed bodies (line 1866). `populate` re-adds them past `DESPAWN_RANGE_M`. They are left out of `MAX_AGENTS_TOTAL`.
   - Scenario: the player drives across the city. Every pedestrian it passes stays physical forever, frozen wherever it was when it fell out of fidelity, sometimes mid-crosswalk. Legacy robotaxis then wait behind it forever.
   - Once there are more than 4096 runtime actors, `synchronize` throws "Runtime actor budget exceeded" and `step()` crashes. Per-tick cost grows on the way there.
   - Fix: release claimed legacy bodies when they leave fidelity (clear `runtimeId` or retire them past the despawn range), and count them in `populate`.

2. **Medium: the no-touch guarantee is not proven for vans and buses.** `dodge.ts:568`, `motion.ts:142`.
   - Their reach is built with `vehicleOfAgent`: robotaxi acceleration 2.5, velocity along the heading, no route.
   - But they are moved by `stepCar`: acceleration 9.5, possible lateral slide, a change in yaw rate within one tick.
   - Scenario: a bus (half-length 6.6 m) that starts turning sweeps its corner about 0.2 m outside the predicted reach. Only the 0.3 m override and the sweep block stand between it and a contact.
   - Fix: build reach from the car model (`vehicleOfCar`), and add vans and buses to the fuzz through `createGameSystems`.

3. **Medium: blocked admission throws inside `step`.** `motion.ts:96`.
   - Any mismatch between the planner and the admission check is a hard crash rather than a deferred spawn.
   - Fix: skip the body and retry the spawn later instead of throwing.

4. **Medium: Ambient Director cards stage nothing.** `activities/system.ts:18`.
   - The `director.stage` event has no consumer, and `mission.scene-request` (`scene-actors.ts:17`) has no producer.
   - Fix: wire director cards to the scene planner.

5. **Low: per-tick cost.**
   - `prepareMotionBodies` does `find`/`findIndex` once per motion, which is O(motions × bodies) (`motion.ts:80-82`).
   - `obstacles()` is rebuilt for every `occupied` sample.
   - Fix: index bodies by id and build obstacles once per tick.

6. **Low: dead code with a clearance bug.** In `scene-actors.ts:37`, legacy robotaxis with no `radius` get 0.5. A future scene person could be planned inside a taxi body, which would hit the throw in finding 3. Fix: use box distance.

Determinism and input mutation: apart from the `Math.hypot` issue above, I found no problem. Copies are taken before every mutation in `synchronize`, the staging code and `prepare`, and the gameplay cache is keyed on object identity.
